# ADR-0017: Metric & scoring algorithms

Status: Accepted
Date: 2026-09-04
Deciders: Phase 0

## Context

Spec §12, §13, §14, §16, §40 require explicit, deterministic, documented, versioned algorithms for
Patch Confidence, Change Risk, and Repository Health, and explicit definitions/formulas for the
objective evaluation metrics. No arbitrary scores.

## Decision

- Three scores — **PCS**, **CRS**, **RHP** — with the full signal / normalization / weight /
  formula / threshold tables in `METRICS.md` §2, versioned as `scoring-model v1.0.0`.
- Each score is deterministic, returns a per-signal contribution breakdown + evidence refs +
  `model_version`, and has documented hard-gate overrides (unresolved CRITICAL / scope violation /
  failing regression -> `BLOCKED` for PCS).
- Constants live in `scoring/model_registry.py`; a CI test asserts they equal the `METRICS.md`
  tables (the code↔doc sync contract). Changing a constant requires a version bump + a doc update
  in the same change.
- 16 objective metrics defined in `METRICS.md` §1 with formula / inputs / interpretation /
  limitations / dataset each. Published values are generated by `benchmarks/runner.py`, never
  hard-coded (Spec §55 Rule 16).
- `mapping-model v1.0.0` (RRF fusion weights) and `pricing-table v1.0.0` are versioned the same
  way.
- All constants are **provisional** and calibrated against a labeled train/held-out split in
  Phase 25 -> `scoring-model v1.1.0` with a changelog.

## Consequences

- Every score is explainable ("why 78? here are the ten contributions") and reproducible.
- Un-calibrated `v1.0.0` numbers will look modest; that is honest and expected.
- Discipline required: no constant that cannot be explained in one line.

## Alternatives considered

- **A learned black-box scorer** — rejected by Spec §13 (must be explicit, explainable,
  reproducible). scikit-learn may fit *documented* weights in calibration, not replace the
  formula.
- **Ad-hoc heuristic scores** — rejected by Spec §12 ("do not use arbitrary scores").
