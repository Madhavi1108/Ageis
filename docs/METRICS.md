## 1. Objective metrics (Spec §40) — 16

Metrics 1–12 are the Specification's set. 13–16 add the economic, competitive, and audit
dimensions the wedge depends on. Published values are always generated by `benchmarks/runner.py`,
never hard-coded.

| # | Metric | Formula | Inputs | Interpretation | Limitations | Dataset |
|---|---|---|---|---|---|---|
| 1 | Issue->Code Mapping Accuracy | `F1(predicted_files, gold_files)`; also `recall@k` | mapping output, gold file lists | localization quality | sensitive to gold-set granularity | benchmark set + acceptance repo |
| 2 | Plan->Implementation Alignment | `(steps_impl / steps_total) * (1 - unplanned_files / max(1, changed_files))` | plan, final diff, traceability | 1.0 = every step done, nothing extra | penalizes legitimate refactors touched in-scope | benchmark set |
| 3 | Test Generation Validity | `tests_valid / tests_generated` (valid = collects + deterministic + has assertions) | test catalog, collect results | usable-test rate | does not measure test strength (see mutation check) | benchmark set |
| 4 | Test Pass Rate | `tests_passed / tests_executed` | sandbox results | context metric | not a goal alone | all runs |
| 5 | Autonomous Repair Success Rate | `repaired_to_green / tasks_entering_repair` | repair ledger | headline autonomy | depends on fault difficulty mix | seeded-fault set |
| 6 | Regression Detection Rate | `injected_regressions_caught / injected_regressions_total` | seeded regressions, regression results | safety-net strength | only measures seeded classes | seeded-regression set |
| 7 | Patch Acceptance Rate | `patches_verified_and_scope_clean / patches_generated` | verification + scope results | end-to-end quality | sensitive to task mix | benchmark set |
| 8 | Scope Compliance | `1 - tasks_with_unjustified_scope_violation / tasks_total` | scope-guard events | should be ~1.0 | — | all runs |
| 9 | Review Defect Detection | `seeded_defects_flagged / seeded_defects_total` | seeded-defect patches, findings | reviewer power | not a false-positive measure | seeded-defect set |
| 10 | Verification Accuracy | `(TP + TN) / total`; **false-complete** `= FP / (FP + TN)` | verdicts vs ground truth | correctness of "done" | needs labeled ground truth | labeled verification set |
| 11 | Mean Repair Iterations | `sum(iterations) / tasks_entering_repair` | repair ledger | efficiency | bounded by `max_iterations` | seeded-fault set |
| 12 | Task Completion Rate | `tasks_completed_verified / tasks_submitted` | task statuses | verified-outcome throughput | — | benchmark + acceptance |
| 13 | Cost per Verified Task (USD) | `total_priced_model_spend / tasks_verified` | per-call token accounting, priced-model table | economic viability | tracks model prices | benchmark set |
| 14 | Task Latency P50 / P95 | percentiles of wall-clock `run`->terminal | job timestamps | responsiveness | dominated by sandbox + frontier calls | all runs |
| 15 | Competitive Resolution-Rate Delta | `aegis_verified_scope_clean_rate - best_reference_agent_rate` on the identical task set | AEGIS + reference-agent outcomes | relative quality standing | reference agents evolve | shared benchmark set |
| 16 | Deterministic Replay Fidelity | `tasks_replaying_to_identical_patch / tasks_sampled` | recorded input + model metadata, replay results | audit readiness | provider non-determinism lowers ceiling | benchmark sample |

**Headline release gate:** false-complete rate (from #10) has a hard ceiling of **2%**. Shipping
above it is not permitted regardless of other scores.

## 2. `scoring-model v1.0.0`

Rules for all three scores: deterministic; each signal normalized to `[0,1]`; weights within a
score sum to `1.0`; every constant has a one-line rationale; stored with a per-signal contribution
breakdown + evidence refs + `model_version`.

### 2.1 Patch Confidence Score (PCS), 0–100 — higher = safer to accept

| Signal | Definition (-> [0,1], higher = better) | Weight | Rationale for the weight |
|---|---|---|---|
| `targeted_pass` | passed / executed targeted tests | 0.22 | direct evidence the change does what was asked |
| `regression_pass` | passed / executed regression tests | 0.22 | direct evidence nothing else broke |
| `review_clean` | `1 - min(1, (2*critical + high + 0.4*medium) / 5)` | 0.15 | reviewer signal; criticals dominate |
| `coverage` | fraction of changed lines covered by executed tests | 0.10 | untested change lines are unverified |
| `scope_clean` | `1.0` none / `0.5` overridden-with-reason / `0.0` unresolved | 0.10 | out-of-scope edits erode trust |
| `size_fit` | `clamp(1 - lines_changed / 400, 0, 1)` | 0.06 | large diffs are harder to be confident in |
| `dep_fit` | `clamp(1 - impacted_callers / 25, 0.2, 1)` | 0.05 | more callers = more ways to be wrong; floored at 0.2 |
| `history_stable` | `1 - churn_percentile_of_touched_files` | 0.04 | churny files are historically fragile |
| `repair_fit` | `clamp(1 - repair_iterations / max_iterations, 0, 1)` | 0.04 | many repair rounds signal a shaky fix |
| `ai_selfconf` | provider-reported confidence, contribution capped | 0.02 | weak signal; small, capped weight |

`PCS_raw = 100 * sum(weight_i * signal_i)`

`security_gate = 1.0` if no security finding >= HIGH; `0.6` if a MEDIUM security finding is open;
`0.0` if a HIGH/CRITICAL security finding is unresolved.

`PCS = round(PCS_raw * security_gate)`

**Hard override:** any unresolved CRITICAL review finding, any unresolved scope violation, or any
failing regression test caps `PCS` at `40` and sets classification `BLOCKED`.

Classification: `>= 85` HIGH · `70–84` MEDIUM · `50–69` LOW · `< 50` VERY LOW / BLOCKED.

### 2.2 Change Risk Score (CRS), 0–100 — higher = riskier

| Signal | Normalization | Weight | Rationale |
|---|---|---|---|
| `files_changed` | `clamp(n / 10, 0, 1)` | 0.10 | breadth of change |
| `lines_changed` | `clamp(loc / 300, 0, 1)` | 0.10 | size of change |
| `dependency_impact` | `clamp(impacted_symbols / 30, 0, 1)` | 0.12 | how much downstream code is exposed |
| `public_api_touched` | `1.0` if an exported symbol / route changes else `0.0` | 0.15 | external contract risk is high-weight |
| `inverse_coverage` | `1 - coverage_of_changed_lines` | 0.13 | untested change lines are the main risk |
| `historical_churn` | churn percentile of touched files | 0.08 | fragile areas |
| `prior_failures` | `clamp(failures_in_area / 3, 0, 1)` | 0.10 | repeat-offender areas |
| `architectural_centrality` | normalized betweenness of touched graph nodes | 0.12 | central code breaks more things |
| `complexity_delta` | `clamp(added_cyclomatic / 20, 0, 1)` | 0.05 | added branching |
| `security_sensitivity` | `1.0` if auth/crypto/exec/serialization/path/network touched else `0.0` | 0.05 | sensitive surface |

`CRS = round(100 * sum(weight_i * signal_i))`

Thresholds: `0–24` LOW · `25–49` MEDIUM · `50–74` HIGH · `75–100` CRITICAL.

### 2.3 Repository Health Profile (RHP), 0–100 — higher = healthier

Weighted sub-scores (each -> [0,1], higher = healthier): maintainability index `0.25`,
test coverage `0.25`, inverse dependency coupling `0.15`, churn stability `0.15`,
documentation ratio `0.10`, CI presence `0.10`.

`RHP = round(100 * sum(weight_i * subscore_i))`

Also emits `risky_modules` = top decile by `centrality * churn * inverse_coverage * complexity`.

The **Task-Specific Risk Profile** restricts RHP inputs to the files in the current impact set and
is attached to the plan and the verification result.

### 2.4 Documentation contract per scoring metric (Spec §13)

Each of PCS / CRS / RHP documents: metric, purpose, signals, normalization, weights, formula,
thresholds, categories, evidence, version. This section is that documentation; the code registry
(`scoring/model_registry.py`) mirrors these tables and the sync test asserts equality.

### 2.5 Unavailable-signal handling (`scoring-model v1.0.0`)

Some signals have no data source in the current build — per-changed-line coverage (no coverage
instrumentation), historical churn (`historical_churn`, `history_stable`, `churn_stability` —
Git history is Phase 19), and sometimes `complexity_delta` (unparseable edit-op bodies). Phase 17
keeps the §2.1–2.3 formulas **exactly** and handles a missing signal with a documented neutral
prior plus a lowered confidence, rather than renormalizing weights.

| Constant | Value | Applies to | Rationale |
|---|---|---|---|
| `UNAVAILABLE_PRIOR_GOOD` | `0.5` | a missing "higher = better" signal (PCS signals, RHP sub-scores) | neither flatter the patch with `1.0` nor punish it with `0.0` for absent instrumentation |
| `UNAVAILABLE_PRIOR_RISK` | `0.0` | a missing "higher = riskier" signal (CRS signals) | absence of evidence is never invented as risk |

Each score also returns `overall_confidence = 1 − Σ(weight of each unavailable signal)` and, in
`per_signal_contributions`, every signal's `basis` (`FACT` / `INFERENCE`) and its
`unavailable_reason` when it fell back to a prior. All `v1.0.0` values are provisional and are
revisited in Phase 25.

## 4. `mapping-model v1.0.0` (for metric #1)

Reciprocal-rank fusion over retrievers (lexical, symbol, graph-proximity, git-history, memory,
semantic-if-available). Fusion score for a candidate `c`: `sum_over_retrievers( w_r / (k + rank_r(c)) )`
with `k = 60`.

| Retriever | Weight `w_r` | Notes |
|---|---|---|
| lexical (FTS over code + docstrings + symbols) | 1.0 | always available |
| symbol-name match | 0.8 | exact / fuzzy qualname |
| graph proximity | 0.9 | k-hop from seed symbols |
| git-history | 0.5 | files in related historical fixes |
| engineering memory | 0.6 | provenance-labelled; never authoritative |
| semantic (embeddings) | 1.0 | only if a provider is configured; absence lowers `overall_confidence` |

Confidence calibration is heuristic in `v1.0.0` (agreement across retrievers + top-score margin);
calibrated in Phase 25.

## 5. Calibration protocol (Phase 25)

- Labeled dataset: benchmark tasks with outcomes (patch accepted / rejected, verified /
  false-complete), disjoint from the acceptance repo, split train / held-out.
- Fit normalization bounds and weights against labels with simple, explainable models; never
  optimize a constant that cannot be explained in one line.
- Bump to `scoring-model v1.1.0` with a changelog; the sync test and this file update together.
- Report measured metric values with confidence intervals and limitations in
  `docs/BENCHMARK_RESULTS.md`.
